## 三句话看懂（大白话版）

**1. 题面泄露词形 → 得分虚高，是真的。**
不是"答案被写进题面"，而是"题面用了和答案同源的词"。我把 8 道题的题面里所有同源词换成同义表达（意思完全不变），
R@1 从 0.625 掉到 **0.000**——说明"排第一"这件事 100% 靠题面里的词形线索，跟语义理解无关。
而 R@10 只掉到 0.75：**"捞得回来"靠语义，"排第一"靠字面。**
更麻烦的是检查工具抓不住：`eval_code.py:79` 只查"完整符号名有没有出现"，
题面写 `MEDUSA`、`EAGLE`（大写/缩写）就完全绕过，18 题报告"0 泄漏"，实为 3 题词根全泄漏。

**2. 大小写问题 → 没解决，一个字节都没动。**
`bm25.py:26` 现在还是 `re.findall(r"[A-Za-z0-9]+", text)`，没有 `.lower()`。
加不加差多少：加 → R@1 0.625→0.750、**R@10 0.875→1.000**（8 题全部进 top10）、
`rejection-sampler` 从"找不到"变第 1 名。**但这是实验结论，不是已实施的改动。**

**3. "银弹"= 万能药。**
"identifier splitting 不是银弹"的白话：**把驼峰名拆成单词这一招，不能一招解决所有检索问题。**
实测验证：对原题面零增益，对改写题面也没救回来——因为改写后题面里根本没有那些词根，索引侧再会拆也无从匹配。

## 一、先说三件做对的

**1. 两条腿都补上了，且对齐生产路径。**
`eval_code.py` 复用 `CodeIndex.search()`（含 module-overview 降权 + cross-encoder 重排），`eval_codegen.py`
走 `agent.run()` 生产 loop。评测的是真实链路，不是另起一套。

**2. chunker 补丁确实生效，且有实证。**
在 48 个真实文件上实测：**342 chunk**（补丁前 337，+5 正好是新增的常量 chunk），
`by_kind = {function 75, method 224, class 33, constant 5, module overview 5}`。
常量 chunk 名单：`PADDING_SLOT_ID ×2`、`_PROFILE_REPLAYS`、`MAX_CHUNK_BYTES`、`_FP32_BYTES`
——后两个正是 `max-chunk-logits` 题需要的。
更强的证据是 agent 产物本身：`workspace/max_chunk.py` 里写着

```python
# Maximum chunk size in bytes for the rejection sampler's FP32 target-logits
# buffer budget (2^30 bytes = 1 GiB).
# Source: rejection_sampler.py:31
MAX_CHUNK_BYTES = 2**30
```

**出处行号 31 正是常量 chunk 的 header 位置**——说明 agent 确实检索到了新补的 chunk。补丁不是摆设。

**3. `route()` 三路拆分正确。**
`write_code`（write/generate/create/implement/produce + 名词）/ `run_python`（run/execute/compute/calculate，
已去掉 write）/ `search`。设计合理，`test_route.py` 的 5 用例锁三类意图也对。

顺带否掉我原本的两个怀疑（**实测证明我错了**）：
- `"__all__".isupper()` → **False**（`isupper` 只看大小写字符，下划线不算）→ `__all__` **不会**被误切成常量。
  实测 5 个常量 chunk 里无单字母、无 dunder。
- 类概览加字段后**没有变长到危险区**：38 个 overview chunk，中位数 412、**最大 1735 字符、超 2000 的 0 个**。
  我最长的一个是 `SpecDecodeBaseProposer`（类 71-1853 行，overview 1735 字符 / 37 行）——仍低于 bge 的 ~2000 字符截断线。

## 二、核心发现：R@1 测的是"术语线索"，不是"语义检索"

这是本轮最重要的结论，用消融实验证明。

### 实验设计

挑 8 道题，把 query 里**与 gold 符号共享的词根全部换成同义表达**（语义等价、但抹掉术语），
跑同一条生产检索路径，看 gold 的排名怎么变。

例（`eagle-spec`，gold = `EagleSpeculator`）：

| | query |
|---|---|
| 原 | Which **speculator** subclass specializes the autoregressive drafting path for **EAGLE**-style draft models? |
| 改写 | Which subclass of the drafting component specialises the one-token-at-a-time generation path for **tree-attention-based assistant** models? |

### 结果

| 指标 | 原 query | 改写 query | 变化 |
|---|---|---|---|
| **R@1** | 0.625 | **0.000** | **−0.625（归零）** |
| MRR | 0.750 | 0.268 | −64% |
| R@10 | 0.875 | 0.750 | −0.125 |

逐题：

| 题 | gold | 原 rank | 改写 rank |
|---|---|---|---|
| medusa | `MedusaProposer` | 2 | 2 |
| multi-mtp | `prepare_input_hidden_states_and_embeddings` | 1 | 2 |
| **eagle-spec** | `EagleSpeculator` | **1** | **掉出 top-10** |
| **hidden-states-extract** | `ExtractHiddenStatesProposer` | **1** | **9** |
| rejection-sampler | `RejectionSampler` | miss | miss |
| suffix-decode | `SuffixDecodingProposer` | 2 | 3 |
| **adaptive-verify** | `AdaptiveVerificationManager` | **1** | **5** |
| mtp | `MTPSpeculator` | 1 | 2 |

### 怎么读

**"捞得回来"（R@10）主要靠语义；"排第一"（R@1）主要靠词形。**
改掉措辞后 R@10 只掉 1 题（0.875→0.75），但 R@1 **全军覆没**。这比实验 13 原来的结论
（"符号粒度语义稀疏，捞得回排不准"）更具体：**排不准的根源是排序分数被术语匹配主导**。

所以 **R@1 = 0.67 不能读作"检索理解实现的能力"**。它混进了一个与检索能力无关的变量：
**出题人有没有把答案的名字写进题面**。

### 出题侧的对应证据

静态体检 18 题 query 与 gold 的词形重叠（`_probe_code_review.py`）：

| 判据 | 结果 |
|---|---|
| 现有泄漏检查（`kw in qa["q"]`，大小写敏感字面） | **0 泄漏**（与实验 13 一致） |
| gold 词根 **100%** 出现在 query | **3 题**：medusa / multi-mtp / eagle-spec |
| gold 词根 ≥50% 出现 | **7 题** |
| 存在 4 字符公共前缀的近似词形 | **12 / 18 题（67%）** |

三处最刺眼的：
- `medusa`：题面直接写 **"MEDUSA"**，gold 是 `MedusaProposer`
- `multi-mtp`：gold 是 `prepare_input_hidden_states_and_embeddings`，题面里
  prepare / input / hidden / states / embeddings **五个词根一个不少**
- `dspark`：题面直接写 **"DSpark"**，gold 是 `DSparkSpeculator`

现有泄漏检查查的是**完整符号名的字面子串**，所以这些都放过（题面写的是 "MEDUSA"，不是 "MedusaProposer"）。
**建议把泄漏检查升级到"词根级 + 专有名词级"**：任何 gold 的 camelCase/snake_case 分段
（长度 ≥3）或专有名词出现在 query 里就报警。这一改，medusa / dspark / gemma4 / eagle-spec /
multi-mtp 会立刻浮出来。

### 局限（必须诚实标注）

1. 这 8 题是我**特意挑的高重叠题**，退化幅度不能外推到全量 18 题（低重叠题本来就靠语义）。
2. 改写是**手工写的**，有主观性。
3. 改写**不只是去词形，也损失了真实信息**——"EAGLE-style" 换成 "tree-attention-based" 后，
   索引里若用 "EAGLE" 表述，等价描述确实更难命中。所以掉分里有一部分是真实的信息损失。

**但第 3 点恰恰是更有价值的读法**：它说明**当用户不知道术语名、只能用语义描述时，R@1 会崩**。
这是真实场景（谁会知道类叫 `ExtractHiddenStatesProposer`？）。所以这个实验的真正启示是
**产品短板，而非评测缺陷**：search_code 目前依赖用户"猜对术语"。

## 三、唯一已验证有效的修复：`text.lower()`

消融实验顺带暴露了它。三个 tokenize 变体的对比（原 query 部分）：

| 变体 | R@1 | MRR | R@10 | rejection-sampler |
|---|---|---|---|---|
| baseline（现状） | 0.625 | 0.750 | 0.875 | **miss** |
| **+ lowercasing** | **0.750** | **0.875** | **1.000** | **rank 1** |
| + lower + identifier split | 0.750 | 0.875 | 1.000 | rank 1 |

**一行 `text.lower()` 让 R@10 满分、R@1 +0.125，并救回了实验 13 唯一那道 miss。**

这**修正了实验 13 的归因**。原文说这道题 miss 是因为"验证/接受类查询被 propose 簇淹没（鲁棒性短板）"。
实测表明：**至少有一部分是 BM25 大小写不匹配**——query 用 "rejecting / verifies"，索引侧是
`RejectionSampler` 的 `_verify` / 注释里的 "reject"，大小写归一化后 BM25 通道就能咬住。

> `bm25.py:26` 的 `re.findall(r"[A-Za-z0-9]+", text)` 不做小写归一化。
> 这是本项目里**投入产出比最高的一行修改**——它同时改善文档检索和代码检索两条腿。

## 四、identifier splitting 不是银弹（推翻我的假设）

我原本的判断：`tokenize` 用 `[A-Za-z0-9]+` 切词，意味着
**camelCase 符号（`ExtractHiddenStatesProposer`）是单个 token，而 snake_case 符号
（`prepare_input_hidden_states_and_embeddings`）天然被拆成词** —— 这正好解释了消融结果里
camelCase 题全崩、snake_case 题不崩。所以我预期"加 identifier splitting 能让改写 query 回升"。

**实测没有。** 加上拆分后：

| | 原 query R@1 | 改写 query R@1 | 改写 query R@10 |
|---|---|---|---|
| + lower | 0.750 | **0.000** | 0.625 |
| + lower + split | 0.750 | **0.000** | 0.875 |

- 原 query 上**零增益**（与只加 lower 完全相同）
- 改写 query 的 **R@1 依然为 0**，只有 R@10 从 0.625 → 0.875
- 个别题**反而变差**：`rejection-sampler` 从 rank 1（lower）掉到 rank 8（lower+split）

原因很清楚：我的改写 query **根本不含符号名的任何词根**，所以拆不拆索引侧都一样对不上。
identifier splitting 只在"用户猜中了部分词"（搜 "hidden states proposer"）时有用。

**结论**：split 可以作为实验留着（对 R@10 有正贡献），但**不要声称它解决了"用户不知道术语"的问题**。
那个问题只能靠**索引侧补自然语言描述**（docstring 合成正是在做这件事，但覆盖面受限于原 docstring 的有无）
或 **query 侧术语扩展**。

> 方法论备注：这是本项目第二次"先怀疑、再实测、发现怀疑错了"。
> 上一次是 `code_chunker` 的装饰器（我怀疑重复，实测是正确的）；这次是 identifier splitting
> （我预期是银弹，实测收益有限）。**源码阅读产生合理的怀疑，只有执行能给答案。**

## 五、代码生成的 facts 判分可被"注释"欺骗

`check_facts` 的判据是 `all(c in code for c in f["contains"])`——**纯字符串共现**。
我做了 5 组实验，全部用 `eval_codegen.check_facts` 真函数判（不调 API）。

### 实验 1：假阳性 —— 值改错、token 留注释

拿 agent 真实产物 `workspace/fp8_apc.py`（正确），只把两个参数值改成错的、
把正确 token 塞进注释：

```python
kv_cache_dtype="auto",  # fp8 needs H100+, falling back to auto
enable_prefix_caching=False,  # True only pays off for long shared prompts
```

facts 要求 `["kv_cache_dtype", "fp8"]` 和 `["enable_prefix_caching", "True"]`。

**判定结果：4/4 全过。** 代码已经**不再启用 FP8 KV cache、也不再启用 APC**，评测给满分。

AST 判据能区分：解析 `LLM(...)` 的 keyword 常量值 → `kv_cache_dtype == "auto"`（正确版是 `"fp8"`）。

### 实验 4：极端假阳性 —— 全注释空壳

```python
# from vllm import LLM, SamplingParams
# llm = LLM(
#     kv_cache_dtype="fp8",
#     enable_prefix_caching=True,
# )
```

**判定结果：4/4 全过，且 `ast.parse` 也通过**（全是注释，语法合法）。
文件对解释器而言是空的，评测给满分。

### 实验 5：6 个静态题全部可被注释空壳骗过

把每个静态题的 `contains` 词全部写进注释行：

| | 结果 |
|---|---|
| 静态题（非 runnable） | 6 题 |
| 被注释空壳拿满分 | **6 / 6** |

**也就是说：12 题里 6 题（fp8-apc / chunked-prefill / lora / structured / ngram-sd / spec-metadata）
的判据是"token 有没有出现"，而 token 可以出现在注释里。**

### 实验 2 / 3：假阴性 —— 注释反而判挂

`not_contains` 同样脆弱，方向相反：

| 实验 | 输入 | 判定 |
|---|---|---|
| 2 | `structured` 正确代码 + 一行注释 `# migrated from guided_json` | **3/4 判挂** |
| 3 | `fix-next-pow2` 正确修复 + 一行注释 `# the old \`1 << n.bit_length()\` was off-by-one` | **1/2 判挂** |

代码完全正确，只因为**说明历史**就被判错。

### 修法：用 AST 判，不用字符串

代码有结构，就不该用字符串匹配。可落地的判据：

```python
# import 检查：ast.ImportFrom 的 module / names，而不是 "from vllm import" 子串
# 参数检查：ast.Call 的 keywords → 用 ast.literal_eval 取常量值比对
def llm_kwargs(code):
    for n in ast.walk(ast.parse(code)):
        if isinstance(n, ast.Call) and getattr(n.func, "id", None) == "LLM":
            for kw in n.keywords:
                yield kw.arg, ast.literal_eval(kw.value)   # kv_cache_dtype -> "fp8"
```

这样：
- `kv_cache_dtype="fp8"` → 真值 `"fp8"` ✓；改成 `"auto"` → 真值 `"auto"` ✗（实验 1 被抓住）
- 注释里的 `guided_json` → **AST 看不见注释** → 不再误判（实验 2 被修好）
- 全注释空壳 → 解析不出任何 `Call` / `ImportFrom` → 判 0 分（实验 4 被抓住）

**改动量很小（一个 `ast_facts()` 函数），收益是把 6 题从"可被欺骗"变成"不可被欺骗"。**

> 注意一个讽刺的对比：**实验 12 的教训是"facts 必须机制型、不能是关键词换句话"，
> 而代码侧的 facts 恰恰退回了"关键词共现"。** 同一个项目、同一个作者、两周内，
> 同一个坑换了层皮又踩了一次。文档侧用 LLM 做语义判定解决了，代码侧因为"看起来是精确匹配"
> 反而放松了警惕——但**精确匹配的前提是匹配对象不可伪造，而注释让 token 变得可伪造**。

## 六、12/12 是 train-on-test

实验 15 的链条是：

1. 加 4 道硬题 → `spec-metadata` / `max-chunk-logits` 挂
2. 归因到"代码索引不切常量/字段"
3. **修 `code_chunker`**
4. 用**同一批 12 题**重跑 → 12/12

第 4 步不是独立验证。修 chunker 的**动机**就是"让这 2 题过"，修完这 2 题过了——
这证明的是"补丁按预期工作"，**不是"补丁普适有效"**。

一个直接的反证：这个补丁在 48 个文件里只切出 **5 个常量 chunk**，
其中 **2 个正是那 2 道题需要的**（`MAX_CHUNK_BYTES`、`_FP32_BYTES`）。
收益高度集中在这 2 题上。要说它有价值，得回答：**vLLM 里还有多少"函数体引用常量名、值在模块级"的情形？**

**验证泛化的正确做法**：拿**不在 12 题里**的、同类需求的新题重跑。例如：
- 另找 2-3 个"需要模块级常量值"的符号（如 `_FP32_BYTES` 之外的其他 buffer 常量）
- 另找 2-3 个"需要类字段"的数据类（`metadata.py` 之外的其他 dataclass）
如果新题也翻绿，补丁才算立住；如果只有原 2 题翻绿，那是**过拟合**。

## 七、仍未解决的老问题

**长 chunk 静默截断**（本轮实测确认仍在）：

| 指标 | 数值 |
|---|---|
| chunk 总数 | 342 |
| 长度中位数 | 990 |
| p90 | 3324 |
| **最大** | **11770** |
| **超 2000 字符** | **91（26.6%）** |
| 超 4000 字符 | 22 |

`bge-base-en-v1.5` 是 BERT-base，上限 512 token ≈ 2000 字符。**26.6% 的代码 chunk 送进 embedding 时被静默截断**
——函数体后半段对向量检索完全不可见，且不报错。同时 `MAX_CODE_CONTEXT_CHARS = 12000`，
单个 11770 字符的 chunk 能吃掉 97% 预算。

这次改 chunker 只加了常量/字段，**没有触及长度问题**。文件顶部注释仍写着"单个函数若极长（罕见），
保持完整不切"——**"罕见"实测不成立，26.6% 都超。**

| `extract_code` **不区分来源** | `eval_codegen.py:45-54` | 落盘优先、回退答案代码块。两种来源语义不同（用没用工具），评分不区分。**本轮实测 12 题产物全在 workspace**，所以"write_file 链路可用"成立——但报告里应显式标注 |
| R@k 的**样本量太小** | `eval_data.CODE_QA_SET` | 18 题，1 题翻转 = 0.056。且 18 题全在 `spec_decode` 一个主题子目录里，**不能外推到整个 vLLM 代码库**（48 文件 / 342 chunk 是个单主题小索引） |

## 九、优先级建议

按"对 coding agent 终局的价值 / 投入"排序：

| 优先级 | 动作 | 理由 |
|---|---|---|
| **P0** | `bm25.tokenize` 加 `.lower()` | 一行；实验已验证有效（R@10 0.875→1.000、R@1 +0.125，救回 1 道 miss），**但本项目尚未落地** |
| **P0** | 泄漏检查升级到词根/专有名词级 | 现在 medusa / eagle / multi-mtp 的词根全在题面、体检却报 0（dspark 题面直接写了 `DSpark`，只因切分规则不同未被统计到）。不改就永远不知道 R@1 里有多少是假的 |
| **P1** | `eval_codegen` 的 facts 改用 AST 判定 | 6/6 静态题现可被空壳注释拿满分。一个 `ast_facts()` 函数解决 |
| **P1** | 补长 chunk 上限（截断并标注，或按逻辑块降级切分） | 26.6% 的 chunk embedding 被静默截断 |
| **P1** | 用新题验证 chunker 补丁的泛化 | 现在的 12/12 是 train-on-test |
| **P2** | 两个脚本落盘 JSON（含模型名/时间/配置） | 已有"实验 7 结论漂移"的教训 |
| **P2** | 记录每题工具调用次数 / 是否撞 `max_steps` | 多轮修复率是 coding agent 的核心指标 |
| **P2** | 主指标换成"改写 query 的 R@10"（或双口径并列） | 原 query 的 R@1 主要反映题面写法，不是检索能力 |
| **P3** | `identifier splitting` 作为实验保留 | 对 R@10 有正贡献，但不是银弹，别过度声称 |

## 十、面试话术

一条可以直接用的表述（把"指标是什么"讲清楚，比报数字有力得多）：

> "代码检索我给 gold 换成符号名之后，R@1 是 0.67。但这个数字我自己做了消融才敢用：
> 把题面里跟符号名共享的词换成同义表达、完全去掉术语线索，**R@1 从 0.625 直接归零，而 R@10 只从 0.875 掉到 0.75**。
> 说明『排第一』主要靠术语命中，『捞得回来』才是语义能力。所以我把 R@10 当主指标，R@1 只当
> 『用户猜对了术语』那个场景的分数。顺带这个消融帮我定位了一个真 bug——BM25 的 tokenizer
> 不做小写归一化，加上 `.lower()` 后 R@10 直接满分，还救回一道我之前误判为『聚类鲁棒性问题』的 miss。"

关于代码生成评测：

> "写代码评测我用三层判分：ast 语法门 → 静态 facts → 纯 Python 题真执行。但我自己测过静态层的强度——
> 拿一个**只有注释**的空壳文件，6 道静态题全部拿满分，因为判据是『token 有没有出现』而注释也是文本。
> 所以我把它改成 AST 判定：解析 `LLM(...)` 的 keyword 取常量值，比对 `kv_cache_dtype` 到底是不是 `"fp8"`。
> 代码有结构，用字符串匹配是自欺欺人。"
